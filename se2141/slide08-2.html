Subchapter 7.9: Database-Design Process

SE 2141 Database Systems

7.9.1 E-R Model and Normalization

How does normalization fit into the overall database-design process[cite: 121]?

  • When we define an E-R diagram carefully and identify all entity sets correctly, the resulting relational schemas usually need very little further normalization.
  • If a generated schema requires normalization, it often points to a flaw in the original E-R design.
    For example, if an instructor entity has a functional dependency dept_name → dept_address, it indicates we should have created a separate department entity in the E-R diagram.
  • The E-R design process naturally tends to generate 4NF designs. (e.g., By automatically creating separate schemas for many-to-many relationships and multivalued attributes).

7.9.2 Naming Conventions

Consistent naming prevents logical errors and aids developers.

  • Unique-Role Assumption: Each attribute name should have a unique meaning. Using number for both a phone number and a room number is dangerous because a join on these attributes would be meaningless.
  • Consistent Generalization: If attributes of different relations have the exact same meaning (like name for both instructors and students), it is best to use the exact same attribute name, especially if you foresee generalizing them into a person entity later.
  • Key Convention: It is standard convention to list primary-key attributes first in a schema definition.

7.9.3 Denormalization for Performance

Occasionally, database designers intentionally choose a schema that has redundant information (i.e., it is not fully normalized).

  • The Goal: To improve read performance for specific, time-critical applications by avoiding expensive JOIN operations on the fly.
  • The Penalty: Extra coding time and execution time are required to keep the redundant copies of data consistent whenever an update occurs.
  • A Better Alternative: Use a normalized schema, but additionally store the required joined data as a materialized view. The database system (not the application code) manages the overhead of keeping the materialized view up to date.

7.9.4 Other Design Issues

A schema can be perfectly normalized (e.g., in BCNF) but still be a terrible design.

  • Creating a New Table Per Year: e.g., total_inst_2017, total_inst_2018. This requires modifying the database schema and rewriting application queries every single year.
  • Crosstabs (New Column Per Year): e.g., dept_year(dept_name, total_2017, total_2018). This also requires schema modification and query rewrites every year.
  • The Solution: Use a single relation with time as data: total_inst(dept_name, year, size). This remains static regardless of how much time passes.

Summary of 7.9

  1. E-R Synergy: A high-quality E-R diagram naturally produces relation schemas that are close to, or already in, BCNF and 4NF. Normalization often acts as a double-check on the conceptual design.
  2. Naming: Enforce the unique-role assumption to avoid meaningless joins, but reuse names consistently when attributes share the exact same conceptual meaning.
  3. Denormalization: Sometimes necessary for extreme read performance, but it burdens the application with maintaining consistency. Materialized views are usually a safer alternative.
  4. Time Series Pitfalls: Never encode data values (like years or categories) into table names or column names; store them as data values within rows to prevent constant schema modifications.
