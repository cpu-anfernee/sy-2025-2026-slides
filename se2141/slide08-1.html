Subchapter 7.1: Features of Good Relational Designs

SE 2141 Database Systems

Conceptual vs. Relational Design

In Chapter 6, we designed conceptual models using E-R diagrams, which provided an excellent starting point for creating a relational database design.

  • The goal of relational database design is to generate a set of relation schemas that allows us to store information without unnecessary redundancy, yet also allows us to retrieve information easily.
  • This is accomplished by designing schemas that are in an appropriate normal form.
  • While some necessary information exists in a well-designed E-R diagram, additional information about the enterprise may be needed to determine if a schema is in a desirable normal form.

The Pitfalls of a Bad Schema

Suppose we combined instructor and department into one schema: in_dep (ID, name, salary, dept_name, building, budget).

  • Redundancy: We have to repeat the department information (building and budget) once for each instructor in the department.
  • Inconsistency Risk: If a user updates the budget amount in one tuple but not all, the database becomes inconsistent.
  • Insertion Anomalies: We cannot directly represent information concerning a newly created department unless that department has at least one instructor, or we resort to using troublesome null values.

Decomposition

The only way to avoid the repetition-of-information problem in a schema like in_dep is to decompose it into several smaller schemas.

  • However, not all decompositions of schemas are helpful.
  • For example, decomposing an employee schema into employee1 (ID, name) and employee2 (name, street, city, salary) is flawed if two employees have the same name.
  • Rejoining these flawed tables will mix data values incorrectly, causing us to lose information about which exact street and salary pertain to which employee.

Lossless vs. Lossy Decomposition

We must insist that all schema decompositions are lossless.

  • Lossless Decomposition: A decomposition where replacing relation $R$ with $R_1$ and $R_2$ results in no loss of information.
  • Formally, projecting a relation $r$ onto $R_1$ and $R_2$, and computing their natural join, gets back exactly $r$ ($\Pi_{R_1}(r) \bowtie \Pi_{R_2}(r) = r$).
  • Lossy Decomposition: A decomposition where computing the natural join of the projections yields a proper superset of the original relation ($r \subset \Pi_{R_1}(r) \bowtie \Pi_{R_2}(r)$).
  • In a lossy decomposition, having more tuples actually means we have less information, because we are unable to represent the absence of a connection between specific attributes.

Normalization Theory

Normalization is the general methodology for deriving a set of schemas that do not suffer from the repetition-of-information problem.

  • First, we decide if a given relation schema is in "good form," known as a normal form.
  • If it is not in good form, we decompose it into a number of smaller relation schemas, each of which is in an appropriate normal form.
  • This decomposition must be a lossless decomposition.
  • We use functional dependencies to determine whether a relation schema is in one of the desirable normal forms.

Subchapter 7.2: Decomposition Using Functional Dependencies

SE 2141 Database Systems

Real-World Constraints

A database models a set of entities and relationships that follow rules in the real world.

  • For example, in a university database:
    • Students and instructors are uniquely identified by their ID.
    • Each department has only one value for its budget, and only one associated building.
  • An instance of a relation that satisfies all such constraints is called a legal instance.

Functional Dependencies ($\alpha \rightarrow \beta$)

While a superkey uniquely identifies an entire tuple, a functional dependency uniquely identifies the values of certain attributes.

  • An instance satisfies $\alpha \rightarrow \beta$ if for all pairs of tuples $t_1$ and $t_2$ where $t_1[\alpha] = t_2[\alpha]$, it is also true that $t_1[\beta] = t_2[\beta]$.
  • Meaning: If two rows have the same value for column $\alpha$, they MUST have the same value for column $\beta$.
  • A functional dependency holds on a schema if every legal instance satisfies it.

Functional Dependencies: Example

Consider the in_dep schema:

in_dep (ID, name, salary, dept_name, building, budget)
  • The functional dependency dept_name → budget holds because for each department, there is exactly one unique budget amount.
  • If two rows share the same dept_name (e.g., both are 'Comp. Sci.'), they must have the exact same budget value.
  • Trivial Dependencies: A functional dependency $\alpha \rightarrow \beta$ is trivial if $\beta \subseteq \alpha$. (e.g., A → A or AB → A).

  2. If we are given the attributes `(firstName, lastName, age)`, is the functional dependency `firstName, lastName → firstName` considered a trivial dependency? Why?

Inference and Closure ($F^+$)

If a set of functional dependencies $F$ holds on a relation, we can infer that other functional dependencies must also hold.

  • Transitivity: If $A \rightarrow B$ and $B \rightarrow C$ hold, we can infer that $A \rightarrow C$ must also hold.
  • We use the notation $F^+$ to denote the closure of set $F$.
  • $F^+$ is the set of all functional dependencies that can be inferred from $F$, and it contains all the original dependencies in $F$.

Testing for Lossless Decomposition

We can use functional dependencies to prove a decomposition is lossless.

  • Let relation $R$ be decomposed into $R_1$ and $R_2$.
  • The decomposition is lossless if at least one of these dependencies is in $F^+$:
    • $R_1 \cap R_2 \rightarrow R_1$
    • $R_1 \cap R_2 \rightarrow R_2$
  • In plain English: The attributes shared between the two new tables ($R_1 \cap R_2$) must form a superkey for at least one of the new tables.

Lossless Decomposition: Example

Decomposing in_dep:

instructor (ID, name, dept_name, salary)
department (dept_name, building, budget)
  • The intersection ($R_1 \cap R_2$) is dept_name.
  • Does dept_name → department? Yes! dept_name → dept_name, building, budget holds because dept_name is the primary key of department.
  • Therefore, this is a lossless decomposition.

The Purpose of Normalization

Normalization provides a formal framework to evaluate if a relational schema is in "good form" and free of structural anomalies.

  • We use functional dependencies to identify if attributes are incorrectly bundled into a single table.
  • If a schema violates the rules of a normal form, we decompose it into smaller, compliant tables.
  • The two most common and important normal forms in standard database design are Boyce-Codd Normal Form (BCNF) and Third Normal Form (3NF).

7.3.1 Boyce-Codd Normal Form (BCNF)

BCNF is one of the more desirable normal forms. It eliminates all redundancy that can be discovered based on functional dependencies.

A relation schema $R$ is in BCNF with respect to a set $F$ of functional dependencies if, for all functional dependencies in $F^+$ of the form $\alpha \rightarrow \beta$ (where $\alpha \subseteq R$ and $\beta \subseteq R$), at least one of the following holds:

  • $\alpha \rightarrow \beta$ is a trivial functional dependency (i.e., $\beta \subseteq \alpha$).
  • $\alpha$ is a superkey for schema $R$.

In plain English: "Every non-trivial determinant must be a superkey."

BCNF Violation Example

Consider the combined schema in_dep (ID, name, salary, dept_name, building, budget).

  • We know that dept_name → building, budget holds true.
  • Is this trivial? No, because building, budget is not a subset of dept_name.
  • Is dept_name a superkey for in_dep? No, because a department name alone cannot uniquely identify an instructor's ID or name.
  • Therefore, in_dep is not in BCNF and must be decomposed!

  1. What two conditions can save a functional dependency $\alpha \rightarrow \beta$ from violating Boyce-Codd Normal Form?
  2. Suppose a relation vehicle (VIN, model, manufacturer, factory_location) has a functional dependency manufacturer → factory_location. Assuming VIN is the only primary key, does this relation satisfy BCNF? Why or why not?

The Limits of BCNF

While BCNF successfully eliminates redundancy, it has one major drawback: achieving it can sometimes prevent dependency preservation.

  • When we decompose a schema, we want to be able to check all our original functional dependencies efficiently.
  • If a decomposition forces us to perform a join across multiple tables just to verify a functional dependency during an insert or update, the decomposition is not dependency-preserving.
  • Because BCNF is so strict, there are some schemas where a lossless, BCNF-compliant decomposition makes it impossible to preserve all dependencies locally.

7.3.2 Third Normal Form (3NF)

To guarantee that we can always preserve dependencies, we use a slightly relaxed standard called Third Normal Form (3NF).

A relation schema $R$ is in 3NF if, for all functional dependencies $\alpha \rightarrow \beta$ in $F^+$, at least one of the following holds:

  • $\alpha \rightarrow \beta$ is a trivial functional dependency.
  • $\alpha$ is a superkey for schema $R$.
  • [The 3NF Exception]: Each attribute $A$ in $\beta - \alpha$ is contained in a candidate key for $R$. (These are known as prime attributes).

Comparing BCNF and 3NF

The third condition in 3NF acts as a safety valve. It allows certain functional dependencies to exist even if their left side isn't a superkey, provided the right side is part of a candidate key.

  • Strictness: BCNF is strictly stronger than 3NF. Any schema in BCNF is automatically in 3NF.
  • The Trade-off:
    • By using 3NF, we are always guaranteed a decomposition that is both lossless and dependency-preserving. However, we may retain a small amount of data redundancy.
    • By using BCNF, we guarantee zero FD-based redundancy, but we might lose dependency preservation.

  2. If you have to choose between BCNF and 3NF for a database design, why might a database architect explicitly choose to stop at 3NF rather than decomposing all the way to BCNF?

Summary of 7.3

  1. BCNF: The gold standard for eliminating redundancy. It demands that for every non-trivial dependency $\alpha \rightarrow \beta$, $\alpha$ must be a superkey.
  2. Decomposition Goal: If a table violates BCNF, we split it using the violating dependency to remove data duplication.
  3. 3NF: A slightly relaxed normal form. It allows non-superkey determinants if the determined attribute is part of a candidate key.
  4. The Trade-off: BCNF prevents all FD-based redundancy, but 3NF is sometimes required to ensure all database constraints can be checked efficiently without joining tables (dependency preservation).
