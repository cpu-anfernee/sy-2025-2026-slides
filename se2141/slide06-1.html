4.1.1 The Natural Join

The natural join operation matches tuples across two relations based on equal values in all common attribute names.

  • Attributes with matching names appear only once in the result relation.
  • Example: Finding courses taken by students: 
    SELECT name, course_id
FROM student NATURAL JOIN takes;
  • Avoiding Erroneous Matches (JOIN USING): Specify precise matching columns to prevent accidental joins on shared attribute names like dept_name: 
    SELECT name, title
FROM (student NATURAL JOIN takes) JOIN course USING (course_id);

4.1.2 Join Conditions (ON Clause)

The ON condition allows general predicates over joined relations, behaving like a WHERE clause during the join:

  • Unlike NATURAL JOIN or USING, the join attribute appears twice in the raw result unless explicitly projected. 
    SELECT *
FROM student JOIN takes ON student.ID = takes.ID;
  • Why use ON? It separates structural join predicates from application filtering predicates, improving readability and altering behavior in outer joins.

4.1.3 Outer Joins

Outer joins preserve tuples that would be lost in an inner join by padding missing attributes with NULL values:

  • Left Outer Join: Preserves unmatched tuples from the left-hand relation. 
    SELECT * FROM student NATURAL LEFT OUTER JOIN takes;
  • Right Outer Join: Preserves unmatched tuples from the right-hand relation. 
    SELECT * FROM takes NATURAL RIGHT OUTER JOIN student;
  • Full Outer Join: Preserves unmatched tuples from both relations (combines Left and Right). 
    SELECT * FROM student NATURAL FULL OUTER JOIN takes;

ON vs WHERE in Outer Joins

The ON clause determines which tuples match to generate null-padded records, while the WHERE clause filters the result after join generation.

-- Example 1: Preserves student 'Snow' padded with NULLs
SELECT * FROM student LEFT OUTER JOIN takes ON student.ID = takes.ID;

-- Example 2: Generates Cartesian Product, then WHERE drops 'Snow'!
SELECT * FROM student LEFT OUTER JOIN takes ON true
WHERE student.ID = takes.ID;

In Example 2, Snow has no matching takes row, so student.ID = takes.ID evaluates to false or unknown and drops the record.

4.2.1 View Definition

A View is a virtual relation defined by a query. It is not precomputed or stored on disk; the query expression is evaluated when accessed.

CREATE VIEW faculty AS
SELECT ID, name, dept_name
FROM instructor;
  • Custom Column Headers: Explicitly name output columns in the view definition: 
    CREATE VIEW departments_total_salary(dept_name, total_salary) AS
SELECT dept_name, SUM(salary)
FROM instructor
GROUP BY dept_name;

4.4 Integrity Constraints

Integrity constraints guard against accidental loss of data consistency.

  • NOT NULL: Prohibits null insertions for designated attributes.
  • UNIQUE: Ensures attribute lists form a superkey (no two rows share the same values, though nulls are permitted).
  • CHECK(P): Enforces that every tuple satisfies predicate $P$. 
    CREATE TABLE section (
    ...
    semester VARCHAR(6) CHECK (semester IN ('Fall', 'Winter', 'Spring', 'Summer')),
    budget NUMERIC(12,2) CHECK (budget > 0)
);

4.4.5 Referential Integrity

Foreign keys require that values appearing in one relation must exist in the primary or unique key of another relation.

CREATE TABLE course (
    ...
    foreign key (dept_name) references department
        on delete cascade
        on update cascade
);
  • Cascading Actions: Deletions or updates in department cascade to delete or update referencing rows in course.
  • Alternatives to CASCADE include SET NULL or SET DEFAULT.

Summary of Chapter 4 (4.1, 4.2, 4.4)

  1. Joins: Natural joins match on common attribute names; Outer joins preserve unmatched records with NULL padding.
  2. Views: Virtual relations evaluated on demand. Materialized views store results for speed, requiring maintenance.
  3. Constraints: NOT NULL, UNIQUE, and CHECK enforce single-relation rules; Foreign keys and cascading triggers maintain referential integrity.
